# ADE command and configuration reference

Setup from zero is in [setup.md](setup.md); the spec is [PLAN.md](PLAN.md).

## Commands

| Command | What it does |
|---|---|
| `ade init` | Onboarding: writes the user config, verifies the token, adds your team's project(s), runs the first sync and `ade doctor`, prints next steps. Prompts in a terminal; scriptable with `--yes`. Self-hosted GitLab: `--host gitlab.example.com/gitlab` (path prefix kept), `--ca-file <pem>` (trusted for the API, manifest fetches and git over https) and `--ssh-port <n>` (clone URLs `ssh://git@host:n/…`); in a terminal a typed host is also asked for the CA and the ssh port. `--ai-gateway <url> --ai-key-env <VAR> [--ai-model-explain\|classify\|draft\|review <model>]` also writes a LiteLLM gateway profile (in a terminal the models are picked from the gateway's `/v1/models`). |
| `ade` / `ade launch [--dry-run]` | Puts you on the dashboard in the zellij session `ade`. Outside zellij: creates the session with the dashboard in its `home` tab, or, when the session runs, focuses the `home` tab (recreating it if it is gone) and attaches; an exited session is resurrected as it was (zellij cannot be addressed before that, so it opens on the tab it had); resurrecting runs every pane of the session, including the suspended task and service panes of the workspace tabs, because zellij's `--force-run-commands` starts all of them. If the `home` tab's dashboard has exited (you quit `ade dash`), ADE opens a fresh `home` tab and closes the dead one. Inside the `ade` session it focuses the `home` tab and exits instead of running a second dashboard. Inside another zellij session (zellij cannot nest sessions) it says so in one line and opens or focuses a `home` tab running `ade dash` there. `host.mode = "plain"` or `"vscode"` runs the dashboard in this terminal. |
| `ade dash` | Runs the dashboard in the current terminal (the `home` tab's command). |
| `ade version` | Prints the version. |
| `ade project add <manifest>` | Registers a project and clones every repo as `<root>/<project>/<repo>/{.bare,<default-branch>}`: the baseline worktree is named after the default branch (`main/`, `develop/`; a `/` in the name becomes `-`). With a `[project]` table it also writes the generated `<root>/<project>/AGENTS.md` and `.ade/shell`, and with `[repo_groups]` writes the group `<workspace>.code-workspace` files. Idempotent. |
| `ade project bootstrap --forge <name> --group <path>` | Generates a team manifest (`.ade.toml`) from an existing GitLab group or GitHub owner: tracker, repos and app values, label patterns, workflow stages, iterations, weight source and run tasks from each repo's root files, validated before it is written. `--publish` opens a merge request adding it to the tracker repo (`--dry-run` shows it first). Never overwrites without `--force`; see [manifest.md](manifest.md#bootstrapping-a-manifest). |
| `ade project list` | Lists the registered projects, their directory, repo count and last update. |
| `ade project status [name]` | Lists repos, worktrees, ahead/behind, and dirty state, with repos under their `[repo_groups]` headings (sorted by group, then ungrouped; `--json` adds `groups` per repo and `repo_groups`). `status` (not `list`) also shows the project-wide parts of `[project]`: the generated AGENTS.md and the shell wrapper with its packages. |
| `ade project remove <name> [--dry-run] [--yes] [--force]` | Unregisters a project and deletes its clones. Refuses (exit 2) when a worktree has uncommitted changes or unpushed commits, and says where; `--force` deletes anyway. |
| `ade dotfiles [--project <name>] [--dry-run]` / `ade dotfiles status` | Applies the `[dotfiles]` repo of each project's manifest, the repo the team uses with `coder dotfiles`: clones it under ADE's data directory (`dotfiles/<project>`; fetched and reset to `origin/<branch>` when it is there, so a force-push is followed and local edits to tracked files are discarded; the old clone moved to `<dir>.backup-<time>` when the URL changed), then runs its install script (`install.sh`, `install`, `bootstrap.sh`, `bootstrap`, `setup.sh`, `setup`, then the same names under `script/`, or `dotfiles.install`), or symlinks its dotfiles into `$HOME` (an existing file becomes `<name>.bak`, or `.bak.1`, ... when that exists; needs an absolute `$HOME`). The script is team code and runs with your environment minus the variables your forges' `token_env` name, plus `ADE_PROJECT`, `ADE_ROOT` and `ADE_DOTFILES_DIR`. `ade setup` runs it as a step; `ade project sync` never does. In a Coder workspace whose own dotfiles step already applied the same repo it does nothing (`applied by coder`). `--dry-run` writes nothing; `status` shows what was last applied. Exits 1 when a project's dotfiles failed. Turn off or redirect in your config with `[dotfiles] enabled = false` or `repo`/`branch`. |
| `ade gc [--dry-run] [--yes]` | Removes worktrees whose merge request is merged or closed, only when clean and pushed; every tree that stays says why, and `--dry-run` says why each removable tree counts as pushed and which branches it would delete (with `-D` unless git sees them merged by then, and why) or only delete if git sees them merged. The local branch goes with the worktree the same way as in `ade cleanup` (`-d`, or `-D` when its commits are all in a merged MR's head), else it stays with the reason. A branch without an upstream counts as pushed only if HEAD is an MR's head commit or is on a remote branch that survives a `fetch --prune` (gc fetches those repos). |
| `ade cleanup <ref> [--dry-run] [--yes]` | Per-item `ade gc`: for the cached work item `<ref>` belongs to (tracker issue, child issue or MR), judges each of its worktrees with gc's checks (every MR of the branch merged or closed, tree clean, everything pushed), then removes the passing worktrees, fast-forwards the repo's default-branch baseline tree after a fetch (only a clean tree with nothing of its own moves) and deletes the local branches: with `git branch -d`, or with `git branch -D` when git sees no merge (a squash merge) but every commit on the branch is in the head commit of a merged MR of it (the head itself or an ancestor; the commit is fetched when the clone lacks it). A branch with commits outside the merged MR stays with that reason; the default branch is never deleted and git refuses a branch checked out in another worktree. Worktrees are never forced. `--dry-run` also says which branches it would delete and why. A tree that fails a check stays with the reason and the command exits 2; `--dry-run` only reports (it still fetches); without `--yes` it asks. `--json` gives the trees (as `ade gc --json` rows, plus `removed` and `branch_kept`) and `baselines`. Audited as `worktree.remove`, `git.branch.delete` and `git.pull`. |
| `ade update` | Refreshes manifests, fetches every repo, and fast‑forwards clean trees (never merges, rebases, or stashes). Also rewrites the generated `AGENTS.md`, `.ade/shell` and the group `.code-workspace` files, and removes a generated file whose manifest key is gone. Exits 2 if any repo failed. |
| `ade start <tracker-ref> [--repo <repo>]… [--branch <repo>=<branch>]… [--mode draft\|branch\|browse] [--child auto\|always\|never] [--layout code\|agent\|manual] [--new-mr] [--dry-run] [--json]` | Starts work on a tracker issue like `s` in the dashboard: a child issue in each repo, the tracker's workflow label, the branch, a draft MR from the repo's template and a worktree, the repo's `hooks.install` in it (output on stderr), then the workspace tab. Idempotent: what exists is reused, so a re-run creates nothing; a worktree missing on this machine is added and installed, and an install that failed or whose lockfiles changed runs again. `--repo` defaults to the repos the app labels route to, or to the manifest's only repo when it has exactly one (the dashboard preselects it too). `--branch repo=branch` (repeatable) names the branch for one repo instead of the one `conventions.branch` derives, for a second set of changes in a sibling repo; the repo is added to the work if it is not chosen yet. The branch is looked up by exact name: an existing branch and its MR are reused (no branch is created, no second MR opened), otherwise the branch is created from the default branch with its own draft MR. The worktree goes to `<repo>/<branch with / as ->`, and an existing worktree of the branch is reused. Unknown repos and values that are not `repo=branch` are refused, and so is `--branch` with `--mode browse`. `--dry-run` shows every write and the MR body, and lists each pinned branch as existing or new. In the start dialog, `b` on a repo row types its branch (empty: the derived name). |
| `ade review <group/project!N> [--no-zellij] [--dry-run]` | Opens the MR in a review workspace tab: the source branch is checked out as a worktree (made when missing; for a fork MR, or a source branch that origin does not have, the worktree is the detached `mr-<iid>` tree at the MR head ref, `refs/merge-requests/<iid>/head` or `refs/pull/<n>/head`, with no branch and so no push from ADE, and the repo's `post_worktree` hooks are not run for a fork: they are printed to run by hand) and the tab uses the `review` layout (the diff against the target branch through delta, lazygit, a shell). `--no-zellij` opens no tab and prints the worktree and the `cd … && git diff … \| delta` command. `ade review add\|list\|rm\|submit` collect and send line comments as one batch. |
| `ade mr describe <group/project!N> (--body-file <file\|-> \| --edit) [--yes] [--dry-run] [--json]` | Replaces the description of an open MR with text you wrote, no AI: read from a file (`-` is stdin) or written in your editor (`--edit`: `host.editor`, else `$VISUAL`/`$EDITOR`, seeded with the current description). Only the description is sent (title, draft state and the rest stay). It prints a line diff against the current text, then asks (`--yes`, or an interactive yes; a script without `--yes` exits 5 and writes nothing); `--dry-run` shows the diff and writes nothing. Audited as `forge.mr.description` with `source: manual` and the length (never the text), dry runs as skipped. Manual text is never stripped of quick actions: on GitLab, lines such as `/close` or `/assign` are run by GitLab when it saves the description, so the preview warns and names them (`quick_actions` in `--json`); GitHub has none. An empty text, an unchanged text and a merged or closed MR are refused. Works on GitLab and GitHub. `ade ai describe` drafts a description with a model instead. |
| `ade mr checkout <group/project!N> [--dry-run] [--json]` | Checks the MR's head out as a detached worktree `<root>/<project>/<repo>/mr-<iid>`, with no workspace tab, to read, run or test someone else's change (`ade review --no-zellij` checks out the source branch instead). The head is the forge's reported commit, else `refs/merge-requests/<iid>/head` (`refs/pull/<n>/head` on GitHub, which covers forks), else `origin/<source>`. A tree that exists moves to the MR's new head only while it is clean. `--json` has `worktree` (the path), `commit` and `action` (`create`, `update`, `keep`). Audited as `git.worktree.add`. |
| `ade mr show <group/project!N> [--json]` | The MR's state, branches, pipeline, approvals and threads. A fork MR (its source branch is in another project) adds a `fork:` line with the source project, and `--json` has `fork` and `source_project`; `ade review` and `w` on the MR page open such an MR detached at its head ref. |
| `ade mr from-branch [dir] [--title …] [--template …] [--target …] [--closes <issue>] [--strip-actions[=names]] [--ready] [--dry-run] [--json]` | Opens the MR for work started outside ADE: the branch checked out in `dir` (default `.`, a worktree under the projects root) gets a draft MR into the repo's default branch. The body is the repo's MR template (`--template`, else `conventions.mr.template`) with `Closes <issue>` first when `--closes` is given; `--strip-actions` removes quick actions as for `ade start`. The title is the one commit's subject, else the branch name in words. Draft unless `conventions.mr.draft = false` or `--ready`; the worktree's recorded commit prefix goes to the forge for the commits it creates. The branch must be pushed; an open MR for it is reported, not duplicated. `--dry-run` prints the MR. Audited as `forge.mr.create`. |
| `ade mr pipeline <group/project!N> [--log <job>] [--tail N] [--json]` | The MR's head pipeline and its jobs, failed jobs first and then in pipeline order: status, stage, name, duration and job id, with the command that shows a failed job's log. `--log` takes a job's name or id and prints the last `--tail` lines (default 50) of its log. Read-only; `ade mr retry` retries the failed jobs. |
| `ade mr rebase <group/project!N> --yes [--skip-ci] [--dry-run] [--json]` | Brings the MR's source branch up to date with its target on the forge, like `u` on the MR page. GitLab rebases the branch (`PUT .../rebase`, which rewrites it: a checkout of it needs a `git reset`; `--skip-ci` starts no pipeline for the new head), GitHub merges the target into it (`update-branch`, pinned to the head you saw). ADE waits for the forge, which works in the background, and says `rebased … onto main`, `updated …: merged main into …` or `… is already up to date`. Refuses without `--yes` (it changes the branch; `--dry-run` sends nothing and needs none) and for an MR that is not open. When the forge cannot do it, in practice a conflict, the branch is untouched, the command exits 1 and prints the exact git commands to run in the worktree (`git fetch origin`, `git rebase origin/<target>`, `git push --force-with-lease origin <source>`; for a fork MR, in its detached `mr-<iid>` tree, pushing to the fork instead of origin); ADE never runs them, and `--json` carries them as `local`. The worktree is found from disk, with no network. `--dry-run` also prints them when the forge already reports conflicts. Audited as `forge.mr.rebase`. |
| `ade mr close <group/project!N> --yes [--dry-run] [--json]`, `ade mr reopen <group/project!N> [--dry-run] [--json]` | Closes an open MR without merging, or reopens a closed one (GitLab `state_event`, GitHub `state`). Closing needs `--yes` unless `--dry-run`; reopening does not. Both read the MR first and refuse a merged MR, or one in the wrong state, before any write. Reopen is refused while another open MR has the same source and target branch. Audited as `forge.mr.close` and `forge.mr.reopen`. No dashboard key: CLI only. Needs no AI. |
| `ade mr request-review <group/project!N> [@user…] [--again] [--dry-run] [--json]` | Asks people to review the MR, or to review it again after you pushed fixes; it needs no AI. Named users who are not reviewers yet are added, and the reviewers already on the MR stay. A named user who already reviews is asked again: their state goes back to requested and they are notified, whatever they said before (approved, commented, changes requested). `--again` also asks every current reviewer, and with no user named it asks only them; with neither it refuses. Usernames may carry the `@`. The command reads the reviewers first and prints whom it asks and what happens to each (`@rae  changes requested: asked again`, `@sam  not a reviewer yet: added`) before it writes anything; `--dry-run` prints that and writes nothing. When only part of a request lands (GitLab: the new users were added but a re-request was refused) it says which users were asked and which were not, and exits non-zero; both parts are audited, the landed users as `ok` and the failed ones as an error. Refuses a merged or closed MR. On GitLab, new users go in with `PUT …/merge_requests/:iid` `reviewer_ids` (the whole set, so the current reviewers are sent along) and existing ones through GraphQL `mergeRequestReviewerRereview` (REST has no re-request call); usernames are resolved with `GET /users?username=`. On GitHub it is `POST …/pulls/:n/requested_reviewers`, which also re-requests someone who reviewed; GitHub refuses the PR's author. `--json` has `targets` (`username`, `action` `add` or `again`, `was`). Audited as `forge.mr.request_review` (`users`, `again`). The MR page's `v` does the same in a dialog. |
| `ade items [--project <name>] [--json]` | Lists the cached work items (no network). With `--json` each item also has a `worktrees` list, `[{repo, path, branch, dirty, has_upstream, ahead, behind}]`: the item's worktrees on disk, found like `ade ws` finds them (a branch that is the source of one of its MRs, or starts with a child issue's iid and a dash), with the state `ade project status` shows. The list is `[]` when the item has no worktree. MR state is in `mrs`. |
| `ade adopt <project> <repo> <branch> [--item <ref>] [--target <branch>] [--from <path>] [--dry-run]` | Brings an existing branch into the layout without any forge write. Fetches the bare clone, then adds `<root>/<project>/<repo>/<branch-dir>` (from the local branch if the bare clone has it, else tracking `origin/<branch>`) and runs the repo's `post_worktree` hooks. `--from` is another local clone or worktree: the branch, with its unpushed commits, is fetched into the bare clone first. A branch that already has a worktree stays where it is. Writes `ade.parent` and `ade.commitPrefix` from `--item` (unset without it) and `ade.target` from `--target` (default: the repo's default branch). Refuses when the directory exists and is not that worktree. Notes when the dashboard cannot link the branch to `--item` yet (no MR from it, no child iid prefix). `--dry-run` prints each step and writes nothing. |
| `ade item <ref> --watch` | The issue-overview pane: the item live from the cache (stations and stage, court and reason, weight and sprint, each child's MR with pipeline and unresolved threads, description and acceptance with task checkboxes, your notes), refreshed within a moment of a cache or record change (fsnotify; polling every 2 s where unavailable). Runs in every dev tab; on a pipe it prints once. |
| `ade item <ref> [--edit]` | Shows an item's record: the snapshot ADE rewrites on each sync, and your notes below `## Notes`, which ADE never touches. Lists the item's worktrees (with `--json`, a `worktrees` field as in `ade items`). `--edit` opens the notes in your editor (`host.editor`, else `$VISUAL`/`$EDITOR`). No network. Your notes are added to agent plan/run/address prompts and to `ade ai summarize`, `draft-reply` and `review` inputs (`--no-notes` leaves them out; they are part of the cache key, and previews say `includes your notes`). |
| `ade note <ref> [text...] [--blocked] [--json]` | Leaves a local note on an item: what stops it, or what you last did. With text it adds a dated line at the end of the item's `## Notes` (`- 2026-11-12 14:20 text`, or `- 2026-11-12 14:20 [blocked] text` with `--blocked`); without text it prints the dated notes, newest first. The record is made from the cache when the item has none yet. Nothing goes to the forge. The dashboard shows the newest notes in the item's side panel, and a row whose newest note is `[blocked]` carries a `blocked` mark until a later note that is not blocked. Free text you wrote in `## Notes` is left as it is and ignored by the parser. Stamps use `user.timezone` (else the local zone). A sync and a note never overwrite each other: both take a lock on the record. |
| `ade issue move <ref> [--to next\|<sprint title or key>] [--with-children\|--no-children] [--dry-run] [--json]` | Moves a tracker issue to the next sprint (or the sprint `--to` names), audited as `forge.issue.sprint`, and raises `issue.iteration_changed` at once. Sets the GitLab iteration (Premium), the milestone (Free, GitHub) or swaps the `Sprint::N` label, by `tracker.iterations.source`. `next` is the first sprint starting after the issue's own sprint; ADE creates no sprint and the error says what to create. Child issues that carry the same sprint follow; `--with-children` moves every open child, `--no-children` none. ADE never closes issues. |
| `ade issue stage <ref> [--dry-run] [--yes] [--json]` | Moves a work item's workflow label to match its derived stage: the move a sync only *reports* under `labels.workflow.sync = "ask"` (the default). It reads the tracker issue again (so a label set by hand since the last sync is respected), prints the change (`add workflow::in review, remove workflow::in progress`) and writes it on `--yes` or a yes at the prompt; `--dry-run` only shows it, and a script without `--yes` is refused (exit 5). Audited as `forge.issue.labels` (`reason: workflow stage`). Works under `sync = "off"` too. Nothing moves, and the reason is printed (exit 0), when the label already matches, says `blocked` (set deliberately), is the team's `done` value, or the item is done. `<ref>` is the tracker issue, a child issue or an MR of the item. Home: `m`. |
| `ade issue weight <ref> <n\|none> [--dry-run] [--no-child]` | Sets or clears an issue's weight, always explicitly and audited as `forge.issue.weight`. Writes the GitLab weight field where the forge licenses it (Premium), else swaps the `weight::N` label and removes the old one. The child issue start work made follows unless `--no-child`. `ade ai classify` suggests a weight from similar closed issues. |
| `ade issue child <tracker-ref> [--repo <repo>]… [--dry-run] [--json]` | The child-issue steps of `ade start` on their own: creates the child in each repo (copying type, assignee, milestone and iteration), links it `relates_to` the tracker issue and places it under it in the forge's hierarchy. No branch, MR, worktree, label move or workspace. Idempotent: an existing child is reused. Audited as `forge.issue.create`, `forge.issue.link` and `forge.issue.parent`. |
| `ade issue assign <ref> [--replace] [--dry-run] [--json]` | Assigns an issue (tracker or child, on any configured forge) to you, keeping the other assignees; `--replace` makes you the only one. An issue you are on already is left alone. Audited as `forge.issue.assign`. |
| `ade ai summarize\|classify\|reply\|review\|models [--profile <name>]` | AI actions on one item through the active profile (pre-flight, caps, cache and audit apply to all). `classify` uses the profile's `classify` model (falls back to `explain`) and asks the gateway for a JSON-schema answer; `models` lists the gateway's models and marks which role uses which. Roles and a LiteLLM example: [setup.md](setup.md#through-a-litellm-gateway). When the model stops at its output limit, the HTTP drivers ask once more with the cap doubled, and the pre-flight estimate covers both calls. An answer still cut short is shown with a "cut short" note beside it (`truncated` in `--json`), never inside the text, and is not cached; asking again without `--refresh` within 30 minutes is refused so the same prompt is not bought twice. |
| `ade ai research <issue-ref> [--detach] [--show] [--refresh] [--dry-run] [--yes] [--override-budget] [--no-notes]` | A stored research job for one issue: goal, open questions, approaches, risks and first steps, from the issue, its tracker parent, its discussion, linked issues, the merge requests already open for it and your notes (the model does not read code). The `plan` role's model (falls back to `explain`). The answer is an AI artifact in the item's record, found again by its input hash, so asking again about an unchanged issue costs $0 (`--refresh` buys a new one). `--detach` shows the pre-flight here (a refusal by a cap exits 4, a needed yes exits 5 without `--yes`), then runs the call in a worker process that outlives the command, the terminal and the dashboard; it is filed in `<records>/items/<forge>/<project>/<iid>/research/job.json` (`running`, `done` or `failed`, with the worker's output in `worker.log`) and raises an `ai.research.done` / `ai.research.failed` notification. A job already running is not started twice; one whose worker died reads as failed. `--show` prints the stored state and answer and spends nothing (it works with `ai.mode = "off"`). `ade item <ref>` lists the job, with `--json` as `research`. `R` on a Home item does the same from the dashboard. |
| `ade ai describe <mr-ref> [--apply] [--template <name>] [--refresh] [--dry-run] [--yes] [--override-budget]` | Drafts a merge request description from the project's MR template (`--template`, else the manifest's `conventions.mr.template`, else `Default`, else the only one; quick actions are stripped from it), the MR's commits and its diff, and prints it as a preview. `--apply` shows what it replaces, asks (`--yes` or an interactive yes; a script without `--yes` exits 5) and writes only the description, audited as `forge.mr.description` (the text is not logged, only its length). Quick actions in the draft are stripped (they would run again on update) and the lines linking work items (`Closes #4`, `Part of …#1`) of the current description are kept. A draft the model did not finish is never applied. Your private notes are not sent: the description is posted. Cached by head SHA, commits and template, and not by the current description, so an unchanged MR costs $0 the second time and applying a draft does not make the next ask a miss. `--dry-run` shows the pre-flight and whether it is cached and sends nothing; `--json` adds `description`, `unchanged` and `applied`. GitLab only for now: another forge says so and stops. Key `B` on the MR page opens the draft in an editor dialog (`enter` writes it to the MR, `ctrl+r` asks again past the cache, `esc` throws it away). |
| `ade ai ci-triage <mr-ref> [--refresh] [--dry-run] [--yes] [--override-budget]` | Triage of the failed jobs of the MR's pipeline: for each job (at most six) a one-sentence cause and a suggested fix, from the last lines of its log, read and cleaned the way the MR page's log viewer reads them. Nothing is written to the forge. Cached by what the logs say, not by job ids, so a retry that fails the same way is free. With no pipeline or no failed job nothing is asked. `--json` adds `failed_jobs`. Key `t` on the CI tab shows the answer under the job list (`J`/`K` scroll it). (`ade ai triage` is a different command: it triages an agent review's drafts.) |
| `ade ai research <issue-ref> --cancel` | Stops the issue's running background research and files it as failed ("cancelled by you"), so a new one can start; works with AI off, needs no key or network. The worker's process group is signalled (so omp, its child, goes too), and only when the pid is still that job's worker (read from `/proc`); a stale pid something else has taken is refused, and where `/proc` is not there to check (macOS) the job is still filed as cancelled but the process is not signalled and its pid is printed. Audited as `research.cancel`. Without a running job it says so. |
| `ade mr reply <ref> <discussion> <body> [--ai-drafted] [--dry-run]` | Replies in a thread (body `-` reads stdin; audited as `forge.thread.reply`). `--ai-drafted` is for text `ade ai draft-reply` wrote: quick actions are neutralised, the reply ends with `<sub>Drafted with AI in ADE</sub>` and the audit entry says `source: ai-draft`. |
| `ade agent plan <tracker-ref>` / `agent address <tracker-ref> [--yes] [--allow-uncapped]` | `plan` asks the agent for a read-only plan of an item started with `ade start`. `address` edits code for the MR's unresolved threads and drafts one reply per thread into the review drafts (pending triage; on submit each is posted as a reply in its thread). Both take `--repo`, `--driver`, `--profile`, `--max-usd`, `--no-notes`, `--dry-run` and `--yes`. `address` first lists the threads it will send (other people's text, to an agent that runs commands) and asks on a terminal; `--yes` skips the question and without a terminal it refuses. Forge text in every prompt sits in `<untrusted source="…">` blocks (the same helper and rule as the other AI prompts: data, not instructions). Needs AI on (`ai.mode` not `off`). |
| `ade agent approve <run>` | Your yes to the plan as `plan.md` is now (edit it first if you like; approving again after an edit approves the edited text). |
| `ade agent diff <run> [--patch]` / `agent review <run>` / `agent list [--all]` / `agent show <run>` / `agent cancel <run>` | `diff` is what the agent changed (new files included, the index untouched; for an accepted run, only the committed work). `review` opens lazygit on the run's tree. `list` and `show` first mark a run whose ADE process died as failed (and kill an agent it left behind). `cancel` stops the process (only the recorded one: a reused pid is left alone) and marks the run cancelled; edits stay in the worktree. |

## Configuration

- **User config:** `~/.config/ade/config.toml`, or `$ADE_CONFIG`. It holds forges and their credential *commands*, `[[projects]]`, and the `[update]` and `[notify]` settings (`[notify.external]` hands budget and long-outage events to a command of yours).
- **Project manifests:** `*.ade.toml`, shareable. They define repos, the dependency graphs, and team conventions.
- **Local overrides:** `config.local.toml` and `<name>.ade.local.toml` beside either file, never shared: tables merge key by key, everything else replaces (PLAN.md §2).
- **Editor:** `host.editor` (`auto`, `nvim`, `ade-nvim`, `code`, `$EDITOR`) picks the editor everywhere ADE opens one; `auto` is `code` inside a VS Code terminal, else `$VISUAL`, else `$EDITOR`, else the first of nvim, vim, vi and nano on PATH. A setting whose editor is missing falls back the same way; `ade doctor`'s `host` / `editor` line warns about it and names the editor in use.
- **Dev environment:** `s` (start work) and `w` open a zellij tab per worktree (`s` on work already started opens its worktree at once when nothing is left to write to the forge, adding it and running its install hooks when it is missing on this machine): a main pane (your editor, or, when `ai.mode` is not `off`, `omp` started with an ADE-generated *implement* skill that carries the ticket, MR, conventions and your notes and stops for review without pushing, or a shell), the item's live overview (`ade item <ref> --watch`), lazygit, a shell, and a strip with the workspace's own tasks (none starts by itself: a pane waits for Enter, Ctrl-C stops one, Enter starts it again). The first time a workspace tab is opened, ADE also creates an unfocused `<tab> · services` tab: its first pane runs the repos' `install` hooks (`ade ws install`), then one pane per service of the run group starts on its own, in dependency order, each waiting for the install and for the services it requires; a service some node requires, with a `port` and no `ready`, counts as ready once the port accepts connections (also in its own pane). Services already running for another workspace are reused, not started twice. `[workspaces.<w>] services = "manual"` skips the tab and keeps the services in the strip, waiting for Enter, with a `services` pane that starts them all. `host.layout = "code" | "agent" | "manual"` is your default main pane (it beats the manifest workspace's `layout`); `a` in the start dialog, `ade start --layout` and `W` on Home pick the other one for a tab. See PLAN.md §6.6. With `ai.mode = "off"` the `agent` layout opens as the editor with a pop-up saying so, `W` only says there is no agent pane and the start dialog offers no `omp` choice; with AI on but `omp` not on `PATH` the agent pane is a shell and a pop-up says so. An agent that commits adds the trailer `Assisted-by: ADE agent`.
- **Fresh without a sync:** dialogs (`c` classify, `s` start work, `=` weight, `N` note, `>` sprint move, `m` label move) read only their own issue and never wait for a running sync; after a write, and after `ade start` or the start dialog created a child and MR, that one item is read again and its cache row replaced, so Home and `ade item --watch` show it at once (no `ade sync`). The next full sync reconciles anything the one-item read could not see.
- **Workflow label:** `m` on a Home item whose preview says `label in progress · stage says in review · m moves it` opens a small dialog that reads the issue again, lists the change (`add workflow::in review`, `remove workflow::in progress`) and writes it on `enter`, audited as `forge.issue.labels`; it is `ade issue stage` in the TUI, and the palette lists it as `Move the workflow label to match the stage`. Under `labels.workflow.sync = "ask"` (the default) nothing else moves the label after `ade start`.
- **Notes on ongoing work:** your notes on an item are the text under `## Notes` in its record, shown in Home's detail pane under `notes` as written (free text and dated lines alike, rendered like the description, the first eight lines with a faint `…` when there is more; `none yet · n writes one` when empty). `n` on Home makes that pane an editor prefilled with the notes (below 110 columns it takes the screen as the `tab` detail view does): `enter` is a newline, `ctrl+s` saves and closes, `esc` also saves and closes (typing is never thrown away), `ctrl+e` saves and opens the record in your editor (`host.editor`) at the notes, the way `ade item <ref> --edit` does. While it is open the other keys type into it and the footer shows its keys. On the MR page, `n` on the Overview tab does the same (on Diff and Review `n` stays deny). Saving writes only the notes section, making the record from the cached item when no sync has written it yet; the pane shows the text at once. `N` on Home opens a one-line form (`ade note` does the same from the shell): type the note, `enter` saves it as a dated line, `esc` cancels; a leading `!` or `tab` marks it blocked, and the newest dated line decides the row's blocked marker. A note written outside the dashboard (`ade note` in another pane, a hand edit) shows within a second: the records are watched. Notes are never sent to the forge and are added to agent and AI prompts.
- **Comments on the tracker issue:** the side panel lists the tracker issue's human comments after the description: a faint `comments · 3 · C shows all`, then the newest two, one line each (author, age, the first line of the body). An issue nobody commented on has no such block; system notes (assignments, label changes) never count. `C` on a Home item opens every comment, oldest first, with its body rendered as markdown: `j`/`k`, `pgup`/`pgdn`, `g`/`G` scroll, `o` opens the issue in the browser, `esc` goes back. The view shows what the last sync kept at once and reads the issue's comments from the forge in the background (`read just now`); when the forge cannot be read it keeps the stored copy and says why. The sync stores the newest `records.snapshot_comments` (default 20) in the item's record (`comments.json` beside `item.md`, and under `## Comments` in the snapshot). Only the tracker issue's comments are shown, not those of child issues or MRs (the MR page's Threads tab has those). `ade item <ref> --watch` shows the newest two under a `comments` rule.
- **AI research, MR description and CI triage:** with AI set up, `R` on a Home item opens its research: none yet (`enter` starts one in the background), running, failed (`enter` tries again) or done, with the answer to scroll; a cost question the caps raise is asked in the dialog, and a refusal says so. The side panel carries a `research` line once an item has a job. On the MR page `B` drafts the description (preview in an editable dialog, `enter` writes it; `E` edits it by hand with no model, see `ade mr describe`, and is there with AI off) and, on the CI tab, `t` triages the failed jobs. All three run through the same pre-flight, caps, result cache, ledger and audit as every `ade ai` call, never block the page, and are absent with `ai.mode = "off"`. See `ade ai research|describe|ci-triage` above.
- **AI text on the forge is marked and defanged:** everything a model drafted that ADE posts ends with a blank line and `<sub>Drafted with AI in ADE</sub>` (`internal/aimark`, idempotent): agent review drafts (every one whose source is not you, when `ade review submit` or `S` uploads them), AI draft replies (the TUI `d` then `enter`, whatever you edited; `ade mr reply --ai-drafted`) and descriptions from `ade ai describe --apply` or `B`. Your own comments and replies are posted as written. GitLab runs quick actions (`/approve`, `/merge`, `/run_pipeline`, `/spend_time` …) in comments, including review comments when the review is published, so every line of AI text that starts with `/command` is neutralised as `\/command` (Markdown shows it unchanged), code blocks included because GitLab's idea of a code block differs by version and nesting; there is no list of action names to go out of date. `ade ai draft-reply` prints the reply as it will be posted, neutralised and marked, and so does the draft reply editor. A reply drafted as a reviewer (you are not the MR's author) is written as a reviewer, and one for an unknown user without promises of code changes.
- **Forge text in prompts is data:** the titles, descriptions, comments, diffs and CI logs that go into a prompt sit in `<untrusted source="…">` blocks, and every such feature's system prompt says to treat them as data, never as instructions. This is hygiene, not a sandbox: what a model writes is still shown or checked before it goes anywhere. CI log tails are masked like the audit log (`glpat-…`, `Authorization:` headers, URL credentials) before they leave the machine, and AI output is masked the same way before it is stored or shown (`redacted: true` in the audit entry). `ade ai review` and the MR page's `A` also read the repo's `AGENTS.md` from the MR's target branch as a guide (`--guide` of the same name replaces it).
- **Unusable answers are not cached, retries and timeouts:** an answer the reader refuses (a review that is not the JSON array, a classify answer that is not the JSON object, no text at all) is paid for and kept in the item's record but never cached: asking again buys a new answer, and the error says so (`--refresh` also skips a cached one). A cached answer the reader refuses is dropped and bought again. In the TUI a retry after a failure (`A`, `d`, `s` on the thread) asks past the cache. A cached answer is shown without the profile's API key being read. The HTTP drivers ask again, at most twice, after a 429 or a 5xx (529 included) waiting as `Retry-After` says (up to 30 s; otherwise 2 s, then 5 s); a budget stop answered with 429 is never retried. The `timeout` of an omp profile bounds one omp call (default 10 minutes), so a hung omp ends instead of locking the issue's research.
- **What the audit log says about a call:** every call that sent a request, failed or retried ones too, records `dest_host` and `bytes`, the request bytes of every attempt (an omp call's destination is `omp`). A call is booked at the price the pre-flight used (the profile's table, else what the gateway publishes, under the bare or the `provider/model` name), so the ledger, the caps and `budget.warn` see it. For a LiteLLM profile each response's `x-litellm-key-spend` updates the provider snapshot; a snapshot whose budget window has reset (`reset_at`) or that is older than an hour no longer refuses calls (the provider still does). omp takes no output cap from ADE: its pre-flight says `omp sets no cap` and is an estimate, and only `budget.call_usd` (`omp --max-cost`) bounds a call.
- **AI off is off:** with `ai.mode = "off"`, `ade ai models` refuses (no key command runs, no provider is called) and `ade budget` and the budget page show the local ledger without reading any billing endpoint.
- **Job logs:** `l` on a CI job opens its log over the whole screen (title line, log, hint line). `j`/`k`, `pgup`/`pgdn`, `g`/`G` scroll, `h`/`l` move sideways, `/` searches (`n`/`N` step through matches, `esc` clears), `esc` closes. ADE reads the last 512 KiB of the log; the title says when the start was cut off. Colour codes are stripped, tabs expand to 8-column stops, other control characters are dropped, a progress line shows its last state, and GitLab section markers show as `── name` headers.
- **Without AI:** ADE works with `ai.mode = "off"` or no profile; AI only adds to it. `config.AI.Available` is the one test every screen uses: AI is available when `ai.mode` is not `off` and `ai.profile` names a defined profile. Where it is not, the AI keys are not listed (Home help `R`, the standup and retro `n`, the MR page's `A`, `B`, `s`, `d`, `t`) and the palette drops the stand-in and research entries; a press of one of them says why once (`No AI on this page: AI is off (ai.mode = off)`). What has a non-AI form stays: `c` classify suggests from keywords, and the palette's digest lists the new comments as they are (`New comments since you last looked`) and moves the last-seen marker, as `ade ai digest --no-ai` does. When a model is set up but cannot answer, classify and the digest fall back the same way instead of ending: classify shows the keyword suggestion labelled `without a model` with the cause (`omp is not installed · …`), the digest lists the comments and says the model could not answer, and declining a pre-flight prompt with `n` does the same (`n use keywords instead` in classify, `n list the comments instead` in the digest; `esc` still cancels). When no keyword fits, classify lists the team's known type and app labels, unticked, to pick by hand (`space` ticks, audited as a manual pick). The header chip reads `AI off` with AI off, nothing with no profile configured, `▲ AI no profile selected` or `▲ AI profile not defined` for a settings mistake, and `▲ AI $0.38 / $2.00 day last call failed` while the newest model call today failed for a reason other than a budget. Failure text is one line, cause and fix, never the raw error (that stays in the audit log): `ai.Human` words AI off, no profile, a missing key or a 401/403, a 429, a missing command, a network error, a timeout, a budget stop.
- **Last working day:** Home opens with a `Last working day` block, with or without AI. The day is the last one before today on which you pushed commits or opened or merged an MR, found in the past two weeks of forge activity rather than from the calendar. The block lists the day's facts (the first five, then `+ n more`); with AI available (`ai.mode` not `off` and `ai.profile` naming a defined profile) it holds a short AI summary of that day instead, in up to three sections (**Shipped**, **In progress**, **Reviews and discussion**). It is asked for once a day, when Home first loads, and the AI cache makes a repeat free. The summary is skipped when the budget is critical (90% or more of any cap), when a budget stop was recorded for the active profile today, or when the call would need confirmation; the block then lists the facts and says why there is no summary. With AI off or no profile configured it lists the facts and says nothing about AI; with profiles configured but none selected (or a missing one) it adds one line naming the setting.
- **Budget alerts:** `budget.warn` comes once per period when spend reaches 80% of a daily, weekly or sprint cap. `budget.stop` is audited for every refused call (a local cap or the provider's budget), but only a profile's first refusal of the local day (`user.timezone`) is a notification (pop-up, inbox, `[notify.external]`), across the dashboard, CLI commands and agents. For the rest of that day ADE makes no AI call nobody asked for on that profile: the last-working-day summary, the sprint retro narrative and the MR page's automatic summary are skipped (a cached answer still shows); the next day they try once more, and a refusal then raises one new alert. A call you ask for is still tried (a reached cap refuses it before anything is sent; the provider may have budget again) and a refusal shows its reason in the dialog, section or CLI output (exit 4), without another pop-up. While a provider stop or a reached cap holds, Home shows one line under the header, `✕ AI budget reached · gw · automatic AI paused until tomorrow · b shows the budget`, and the header chip turns red (`stopped` or `cap`); both clear by themselves when the day ends or spend is back under the cap.
- **Your sprint retro:** `V` opens on your own work in the sprint (`ade sprint review --mine`): what you committed and took on mid-sprint, what you completed, what is in progress and how far it got (`in review`, `draft MR`, `branch`, with its open MRs), what you have not started, and your velocity over recent sprints (only issues assigned to you). The team's burn-down and epics are left out; `m` switches to the whole team's sprint review, which keeps them. Progress is the item's stage in the sync cache; an unfinished item the cache does not hold (someone else's, in an older sprint) reads `carried, progress unknown`.
- **Retro narrative:** opening the page writes its AI narrative under the same rule. Your retro has **Outcome**, **Completed** (in date order), **In progress**, **Not started** and **Velocity**; the team review has **Outcome**, a **Timeline** of what landed in date order, **Carried over** and **Velocity**. Skipped or failed automatic runs stay quiet; `n` on the page still asks on demand: in `ask` mode a call that needs a yes asks inline (`y` sends, `n` or `esc` sends nothing), and the key is only listed in the footer while AI is available.
- **Sprint review with several projects:** `V` opens the review on the first project that has sprints and names it in the page header; `p` cycles the projects (the key and its footer hint appear only when two or more projects have sprints). `ade sprint review` and `ade sprint velocity` without `--project` do the same and say which project they chose in the warnings (`velocity` prints it on stderr). When no project has sprints they fail with `no project has sprints`.
- **Agent runs:** every agent process ADE starts (`ade agent plan|run|address`, and the `omp` pane of the `agent` layout) has `ADE_AGENT_RUN=1` in its environment. ADE's own push (`ade agent push`) does not, so a global `pre-push` hook can refuse any push made while the variable is set (sample in manifest.md). It is a guardrail, not a sandbox: the agent still has the forge token in its environment (only the read token, when the forge sets one).
- **Agent run safety:** `ade agent run` takes `--allow-uncapped`, and `agent discard` takes `--yes`. The caps: every call is limited to the smaller of the run's remaining `budget.agent_run_usd` (0 means no run cap) and what `daily_usd`, `weekly_usd` and `sprint_usd` leave, and a run that would start with nothing left waits instead of failing. codex reports cost only when a turn completes, so it cannot be stopped at a cap mid-edit: `run` and `address` refuse it while any cap applies unless you pass `--allow-uncapped` (the TUI asks; the yes is audited as `agent.allow-uncapped`); the cap then only shows after the turn. `ai.mode = "off"` refuses every step, including an already approved plan and `--background`. One agent per worktree: a second run in a tree with a live run is refused. `agent run --background` runs its checks before it detaches and raises `agent.run.failed` if setup fails after. `agent discard` on a run in review that worked in the item's own worktree puts the tree back to the commit it started from (tracked files reset, untracked removed; refused when the branch has moved or any file differs from the tree the agent left: it lists what is yours), after a confirmation; in the TUI that is `x`. While `ADE_AGENT_RUN=1` is set, ade refuses commands that write to a forge, approve, accept a triage, submit a review or start an agent (`ade review submit`, `ade mr reply|merge|approve|…`, `ade ai triage accept|deny|edit`, `ade agent plan|run|approve|push|…`); every runnable command is classified in `internal/cli/agentguard.go` (refused, or allowed with a reason; a test fails for an unclassified one, so a new write command cannot land unguarded). `init`, `setup`, `config`, `doctor`, `prompt` and `version` replace the root pre-run hook and so are not checked; none writes to a forge. A pid recorded without a start time (runs made before this) is never killed by `cancel` or reconcile: the run is marked and the pid printed for you to check. Quitting the dashboard (or a closed terminal, SIGHUP) cancels a run it started and marks it cancelled; its edits stay. claude runs start with `--strict-mcp-config`, `--setting-sources user` and `--disable-slash-commands`, with Edit/Write denied in required repos; codex gets no `--add-dir`. Known token values are masked in `transcript.jsonl`.
- **Commit prefix:** `conventions.commit_prefix = "GL-{parent}"` in the manifest prefixes the first commit of the MR only (agent prompts state the expanded prefix, or that the project sets none): ADE's agent commit while the branch has none ahead of the target, the GitHub start commit and the squash message it sends. It is written per worktree (`ade.parent`, `ade.commitPrefix`, `ade.target`) for your own commit-msg hook; manifest.md has the hook.
- **Schema:** `schema/{config,manifest}.schema.json`. `ade init`, `ade setup` and `ade config schema --install` wire the user config to a copy beside it; `ade project bootstrap` writes a manifest URL. Elsewhere, put `#:schema <path or URL>` on the first line of a TOML file.
- **Read and write tokens:** `[forges.<name>]` takes `read_token_env` / `read_token_cmd` beside `token_env` / `token_cmd`. With a read token, reads (sync, dashboards, AI context, clone and fetch) use it, only writes and `git push` use the token, and agents ADE launches do not inherit the token's `token_env`. `ade init` / `ade setup` accept `--read-token-env` / `--read-token-cmd`. See [setup.md](setup.md#a-read-token-and-a-write-token).
- **Self-hosted forges:** `[forges.<name>]` takes `ca_file` (PEM bundle; `SSL_CERT_FILE` also works), `ssh_port` and `max_concurrency` (default 4) besides `url`, which may carry a path prefix. Manifest: `repos.<r>.devshell = "auto" | "direnv" | "nix" | "none"` runs a repo's panes, tasks and services inside its dev shell ([manifest.md](manifest.md#dev-shell-per-repo)). Setup: [setup.md](setup.md#self-hosted-gitlab).
- **Reviewer group:** `conventions.mr.reviewer_group = "acme/reviewers"` makes start work request review from that group when it opens the MR: on GitLab the group's active members (you excluded) become the MR's reviewers (Free keeps one), on GitHub the team `org/team-slug` of the repository's owner is requested after the PR exists. The dry run and `--json` show the request; an unreadable group is a warning and the MR is opened without it, and a template's `/assign_reviewer` still applies ([manifest.md](manifest.md#starting-work)).
- **Project-wide setup:** the manifest's `[project]` table (`agents`, `packages` + `nixpkgs`) makes `ade project add` / `ade update` write `<root>/<project>/AGENTS.md` and `.ade/shell`; panes, tasks and services run through the shell when packages are set ([manifest.md](manifest.md#project-wide-setup)).
- **Palette:** `:` opens the command palette on Home, Worktrees and the MR page; every key of each page's help is an entry, so a terminal that swallows keys (a web tty) still reaches every action by name.
- **Small screens:** the dashboard shows fewer regions at once instead of squeezing them. Below 110 columns it is a single pane: `tab` swaps the list for the selected item's detail (Home, Worktrees, Budget, Log; the MR page's Threads and Diff tabs take turns the same way), `e` opens Activity, `i` the notifications, `?` the keys; the footers of Home, Worktrees, Budget and Log always keep `tab details` (or `tab list`), the way out and `? keys`, and every footer drops its other hints from the right. From 110 columns the list and the preview sit side by side, from 140 a rail with Activity and Services joins them. Below 24 rows the blank row under the header and Home's station legend go, the preview's station list loses its connector rows when it does not fit, and one pop-up shows at a time. The header drops the project count, then the sync activity, then the AI chip, as the line gets narrow. A dialog or the help taller than the screen keeps its title and key row: the help scrolls with `j/k` (`ctrl+d`/`ctrl+u`, `g`/`G`), other dialogs show `… n more rows` where the middle was cut. The smallest screen laid out is 60 × 16 ([DESIGN.md](../DESIGN.md#layout) has the numbers).

## Sandbox

Synthetic GitLab and GitHub data for development. Nothing here touches your real config. The sandbox talks to real forges and needs sandbox tokens (`GITLAB_PAT` in `.env`, a `gh` login); with none, run `nix develop -c bash scripts/demo.sh` for the fake GitLab instead ([setup.md](setup.md#6-try-it-offline)). Source `env.sh` from any directory; the `go run` commands below still run from the repo root:

```sh
. scripts/sandbox/env.sh        # isolates state under ./.sandbox, reads GITLAB_PAT from .env
go run ./cmd/ade project add scripts/sandbox/manifests/gitlab.ade.toml
go run ./cmd/ade project add scripts/sandbox/manifests/github.ade.toml
go run ./cmd/ade dash
```

`scripts/sandbox/{gitlab,github}-seed.sh` (re)create the remote sandbox data idempotently.
