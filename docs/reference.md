# ADE command and configuration reference

Setup from zero is in [setup.md](setup.md); the spec is [PLAN.md](PLAN.md).

## Commands

| Command | What it does |
|---|---|
| `ade init` | Onboarding: writes the user config, verifies the token, adds your team's project(s), runs the first sync and `ade doctor`, prints next steps. Prompts in a terminal; scriptable with `--yes`. Self-hosted GitLab: `--host gitlab.example.com/gitlab` (path prefix kept), `--ca-file <pem>` (trusted for the API, manifest fetches and git over https) and `--ssh-port <n>` (clone URLs `ssh://git@host:n/…`); in a terminal a typed host is also asked for the CA and the ssh port. `--ai-gateway <url> --ai-key-env <VAR> [--ai-model-explain\|classify\|draft\|review <model>]` also writes a LiteLLM gateway profile (in a terminal the models are picked from the gateway's `/v1/models`). |
| `ade` / `ade launch [--dry-run]` | Puts you on the dashboard in the zellij session `ade`. Outside zellij: creates the session with the dashboard in its `home` tab, or, when the session runs, focuses the `home` tab (recreating it if it is gone) and attaches; an exited session is resurrected as it was (zellij cannot be addressed before that, so it opens on the tab it had); resurrecting runs every pane of the session, including the suspended task and service panes of the workspace tabs, because zellij's `--force-run-commands` starts all of them. If the `home` tab's dashboard has exited (you quit `ade dash`), ADE opens a fresh `home` tab and closes the dead one. Inside the `ade` session it focuses the `home` tab and exits instead of running a second dashboard. Inside another zellij session (zellij cannot nest sessions) it says so in one line and opens or focuses a `home` tab running `ade dash` there. `host.mode = "plain"` or `"vscode"` runs the dashboard in this terminal. |
| `ade dash` | Runs the dashboard in the current terminal (the `home` tab's command). |
| `ade version` | Prints the version. |
| `ade project add <manifest>` | Registers a project and clones every repo as `<root>/<project>/<repo>/{.bare,<default-branch>}`: the baseline worktree is named after the default branch (`main/`, `develop/`; a `/` in the name becomes `-`). With a `[project]` table it also writes the generated `<root>/<project>/AGENTS.md` and `.ade/shell`, and with `[repo_groups]` writes the group `<workspace>.code-workspace` files. Idempotent. |
| `ade project bootstrap --forge <name> --group <path>` | Generates a team manifest (`.ade.toml`) from an existing GitLab group or GitHub owner: tracker, repos and app values, label patterns, workflow stages, iterations, weight source and run tasks from each repo's root files, validated before it is written. `--publish` opens a merge request adding it to the tracker repo (`--dry-run` shows it first). Never overwrites without `--force`; see [manifest.md](manifest.md#bootstrapping-a-manifest). |
| `ade project list` | Lists the registered projects, their directory, repo count and last update. |
| `ade project status [name]` | Lists repos, worktrees, ahead/behind, and dirty state, with repos under their `[repo_groups]` headings (sorted by group, then ungrouped; `--json` adds `groups` per repo and `repo_groups`). `status` (not `list`) also shows the project-wide parts of `[project]`: the generated AGENTS.md and the shell wrapper with its packages. |
| `ade project remove <name> [--dry-run] [--yes] [--force]` | Unregisters a project and deletes its clones. Refuses (exit 2) when a worktree has uncommitted changes or unpushed commits, and says where; `--force` deletes anyway. |
| `ade dotfiles [--project <name>] [--dry-run]` / `ade dotfiles status` | Applies the `[dotfiles]` repo of each project's manifest, the repo the team uses with `coder dotfiles`: clones it under ADE's data directory (`dotfiles/<project>`; fetched and reset to `origin/<branch>` when it is there, so a force-push is followed and local edits to tracked files are discarded; the old clone moved to `<dir>.backup-<time>` when the URL changed), then runs its install script (`install.sh`, `install`, `bootstrap.sh`, `bootstrap`, `setup.sh`, `setup`, then the same names under `script/`, or `dotfiles.install`), or symlinks its dotfiles into `$HOME` (an existing file becomes `<name>.bak`, or `.bak.1`, ... when that exists; needs an absolute `$HOME`). The script is team code and runs with your environment minus the variables your forges' `token_env` name, plus `ADE_PROJECT`, `ADE_ROOT` and `ADE_DOTFILES_DIR`. `ade setup` runs it as a step; `ade project sync` never does. In a Coder workspace whose own dotfiles step already applied the same repo it does nothing (`applied by coder`). `--dry-run` writes nothing; `status` shows what was last applied. Exits 1 when a project's dotfiles failed. Turn off or redirect in your config with `[dotfiles] enabled = false` or `repo`/`branch`. |
| `ade gc [--dry-run] [--yes]` | Removes worktrees whose merge request is merged or closed, only when clean and pushed; every tree that stays says why, and `--dry-run` says why each removable tree counts as pushed. A branch without an upstream counts as pushed only if HEAD is an MR's head commit or is on a remote branch that survives a `fetch --prune` (gc fetches those repos). |
| `ade cleanup <ref> [--dry-run] [--yes]` | Per-item `ade gc`: for the cached work item `<ref>` belongs to (tracker issue, child issue or MR), judges each of its worktrees with gc's checks (every MR of the branch merged or closed, tree clean, everything pushed), then removes the passing worktrees, fast-forwards the repo's default-branch baseline tree after a fetch (only a clean tree with nothing of its own moves) and deletes the local branches with `git branch -d`, which keeps one git does not see as merged (a squash merge). Nothing is forced. A tree that fails a check stays with the reason and the command exits 2; `--dry-run` only reports (it still fetches); without `--yes` it asks. `--json` gives the trees (as `ade gc --json` rows, plus `removed` and `branch_kept`) and `baselines`. Audited as `worktree.remove`, `git.branch.delete` and `git.pull`. |
| `ade update` | Refreshes manifests, fetches every repo, and fast‑forwards clean trees (never merges, rebases, or stashes). Also rewrites the generated `AGENTS.md`, `.ade/shell` and the group `.code-workspace` files, and removes a generated file whose manifest key is gone. Exits 2 if any repo failed. |
| `ade start <tracker-ref> [--repo <repo>]… [--branch <repo>=<branch>]… [--mode draft\|branch\|browse] [--child auto\|always\|never] [--layout code\|agent\|manual] [--dry-run] [--json]` | Starts work on a tracker issue like `s` in the dashboard: a child issue in each repo, the tracker's workflow label, the branch, a draft MR from the repo's template and a worktree, then the workspace tab. Idempotent: what exists is reused, so a re-run creates nothing. `--repo` defaults to the repos the app labels route to. `--branch repo=branch` (repeatable) names the branch for one repo instead of the one `conventions.branch` derives, for a second set of changes in a sibling repo; the repo is added to the work if it is not chosen yet. The branch is looked up by exact name: an existing branch and its MR are reused (no branch is created, no second MR opened), otherwise the branch is created from the default branch with its own draft MR. The worktree goes to `<repo>/<branch with / as ->`, and an existing worktree of the branch is reused. Unknown repos and values that are not `repo=branch` are refused, and so is `--branch` with `--mode browse`. `--dry-run` shows every write and the MR body, and lists each pinned branch as existing or new. In the start dialog, `b` on a repo row types its branch (empty: the derived name). |
| `ade review <group/project!N> [--no-zellij] [--dry-run]` | Opens the MR in a review workspace tab: the source branch is checked out as a worktree (made when missing) and the tab uses the `review` layout (the diff against the target branch through delta, lazygit, a shell). `--no-zellij` opens no tab and prints the worktree and the `cd … && git diff … \| delta` command. `ade review add\|list\|rm\|submit` collect and send line comments as one batch. |
| `ade mr checkout <group/project!N> [--dry-run] [--json]` | Checks the MR's head out as a detached worktree `<root>/<project>/<repo>/mr-<iid>`, with no workspace tab, to read, run or test someone else's change (`ade review --no-zellij` checks out the source branch instead). The head is the forge's reported commit, else `refs/merge-requests/<iid>/head` (`refs/pull/<n>/head` on GitHub, which covers forks), else `origin/<source>`. A tree that exists moves to the MR's new head only while it is clean. `--json` has `worktree` (the path), `commit` and `action` (`create`, `update`, `keep`). Audited as `git.worktree.add`. |
| `ade mr from-branch [dir] [--title …] [--template …] [--target …] [--closes <issue>] [--strip-actions[=names]] [--ready] [--dry-run] [--json]` | Opens the MR for work started outside ADE: the branch checked out in `dir` (default `.`, a worktree under the projects root) gets a draft MR into the repo's default branch. The body is the repo's MR template (`--template`, else `conventions.mr.template`) with `Closes <issue>` first when `--closes` is given; `--strip-actions` removes quick actions as for `ade start`. The title is the one commit's subject, else the branch name in words. Draft unless `conventions.mr.draft = false` or `--ready`; the worktree's recorded commit prefix goes to the forge for the commits it creates. The branch must be pushed; an open MR for it is reported, not duplicated. `--dry-run` prints the MR. Audited as `forge.mr.create`. |
| `ade mr pipeline <group/project!N> [--log <job>] [--tail N] [--json]` | The MR's head pipeline and its jobs, failed jobs first and then in pipeline order: status, stage, name, duration and job id, with the command that shows a failed job's log. `--log` takes a job's name or id and prints the last `--tail` lines (default 50) of its log. Read-only; `ade mr retry` retries the failed jobs. |
| `ade items [--project <name>] [--json]` | Lists the cached work items (no network). With `--json` each item also has a `worktrees` list, `[{repo, path, branch, dirty, has_upstream, ahead, behind}]`: the item's worktrees on disk, found like `ade ws` finds them (a branch that is the source of one of its MRs, or starts with a child issue's iid and a dash), with the state `ade project status` shows. The list is `[]` when the item has no worktree. MR state is in `mrs`. |
| `ade adopt <project> <repo> <branch> [--item <ref>] [--target <branch>] [--from <path>] [--dry-run]` | Brings an existing branch into the layout without any forge write. Fetches the bare clone, then adds `<root>/<project>/<repo>/<branch-dir>` (from the local branch if the bare clone has it, else tracking `origin/<branch>`) and runs the repo's `post_worktree` hooks. `--from` is another local clone or worktree: the branch, with its unpushed commits, is fetched into the bare clone first. A branch that already has a worktree stays where it is. Writes `ade.parent` and `ade.commitPrefix` from `--item` (unset without it) and `ade.target` from `--target` (default: the repo's default branch). Refuses when the directory exists and is not that worktree. Notes when the dashboard cannot link the branch to `--item` yet (no MR from it, no child iid prefix). `--dry-run` prints each step and writes nothing. |
| `ade item <ref> --watch` | The issue-overview pane: the item live from the cache (stations and stage, court and reason, weight and sprint, each child's MR with pipeline and unresolved threads, description and acceptance with task checkboxes, your notes), refreshed within a moment of a cache or record change (fsnotify; polling every 2 s where unavailable). Runs in every dev tab; on a pipe it prints once. |
| `ade item <ref> [--edit]` | Shows an item's record: the snapshot ADE rewrites on each sync, and your notes below `## Notes`, which ADE never touches. Lists the item's worktrees (with `--json`, a `worktrees` field as in `ade items`). `--edit` opens the notes in your editor (`host.editor`, else `$VISUAL`/`$EDITOR`). No network. Your notes are added to agent plan/run/address prompts and to `ade ai summarize`, `draft-reply` and `review` inputs (`--no-notes` leaves them out; they are part of the cache key, and previews say `includes your notes`). |
| `ade note <ref> [text...] [--blocked] [--json]` | Leaves a local note on an item: what stops it, or what you last did. With text it adds a dated line at the end of the item's `## Notes` (`- 2026-11-12 14:20 text`, or `- 2026-11-12 14:20 [blocked] text` with `--blocked`); without text it prints the dated notes, newest first. The record is made from the cache when the item has none yet. Nothing goes to the forge. The dashboard shows the newest notes in the item's side panel, and a row whose newest note is `[blocked]` carries a `blocked` mark until a later note that is not blocked. Free text you wrote in `## Notes` is left as it is and ignored by the parser. Stamps use `user.timezone` (else the local zone). A sync and a note never overwrite each other: both take a lock on the record. |
| `ade issue move <ref> [--to next\|<sprint title or key>] [--with-children\|--no-children] [--dry-run] [--json]` | Moves a tracker issue to the next sprint (or the sprint `--to` names), audited as `forge.issue.sprint`, and raises `issue.iteration_changed` at once. Sets the GitLab iteration (Premium), the milestone (Free, GitHub) or swaps the `Sprint::N` label, by `tracker.iterations.source`. `next` is the first sprint starting after the issue's own sprint; ADE creates no sprint and the error says what to create. Child issues that carry the same sprint follow; `--with-children` moves every open child, `--no-children` none. ADE never closes issues. |
| `ade issue weight <ref> <n\|none> [--dry-run] [--no-child]` | Sets or clears an issue's weight, always explicitly and audited as `forge.issue.weight`. Writes the GitLab weight field where the forge licenses it (Premium), else swaps the `weight::N` label and removes the old one. The child issue start work made follows unless `--no-child`. `ade ai classify` suggests a weight from similar closed issues. |
| `ade issue child <tracker-ref> [--repo <repo>]… [--dry-run] [--json]` | The child-issue steps of `ade start` on their own: creates the child in each repo (copying type, assignee, milestone and iteration), links it `relates_to` the tracker issue and places it under it in the forge's hierarchy. No branch, MR, worktree, label move or workspace. Idempotent: an existing child is reused. Audited as `forge.issue.create`, `forge.issue.link` and `forge.issue.parent`. |
| `ade issue assign <ref> [--replace] [--dry-run] [--json]` | Assigns an issue (tracker or child, on any configured forge) to you, keeping the other assignees; `--replace` makes you the only one. An issue you are on already is left alone. Audited as `forge.issue.assign`. |
| `ade ai summarize\|classify\|reply\|review\|models [--profile <name>]` | AI actions on one item through the active profile (pre-flight, caps, cache and audit apply to all). `classify` uses the profile's `classify` model (falls back to `explain`) and asks the gateway for a JSON-schema answer; `models` lists the gateway's models and marks which role uses which. Roles and a LiteLLM example: [setup.md](setup.md#through-a-litellm-gateway). When the model stops at its output limit, the HTTP drivers ask once more with the cap doubled, and the pre-flight estimate covers both calls. An answer still cut short is shown with a "cut short" note beside it (`truncated` in `--json`), never inside the text, and is not cached; asking again without `--refresh` within 30 minutes is refused so the same prompt is not bought twice. |
| `ade ai research <issue-ref> [--detach] [--show] [--refresh] [--dry-run] [--yes] [--override-budget] [--no-notes]` | A stored research job for one issue: goal, open questions, approaches, risks and first steps, from the issue, its tracker parent, its discussion, linked issues, the merge requests already open for it and your notes (the model does not read code). The `plan` role's model (falls back to `explain`). The answer is an AI artifact in the item's record, found again by its input hash, so asking again about an unchanged issue costs $0 (`--refresh` buys a new one). `--detach` shows the pre-flight here (a refusal by a cap exits 4, a needed yes exits 5 without `--yes`), then runs the call in a worker process that outlives the command, the terminal and the dashboard; it is filed in `<records>/items/<forge>/<project>/<iid>/research/job.json` (`running`, `done` or `failed`, with the worker's output in `worker.log`) and raises an `ai.research.done` / `ai.research.failed` notification. A job already running is not started twice; one whose worker died reads as failed. `--show` prints the stored state and answer and spends nothing (it works with `ai.mode = "off"`). `ade item <ref>` lists the job, with `--json` as `research`. `R` on a Home item does the same from the dashboard. |
| `ade ai describe <mr-ref> [--apply] [--template <name>] [--refresh] [--dry-run] [--yes] [--override-budget]` | Drafts a merge request description from the project's MR template (`--template`, else the manifest's `conventions.mr.template`, else `Default`, else the only one; quick actions are stripped from it), the MR's commits and its diff, and prints it as a preview. `--apply` shows what it replaces, asks (`--yes` or an interactive yes; a script without `--yes` exits 5) and writes only the description, audited as `forge.mr.description` (the text is not logged, only its length). Quick actions in the draft are stripped (they would run again on update) and the lines linking work items (`Closes #4`, `Part of …#1`) of the current description are kept. A draft the model did not finish is never applied. Your private notes are not sent: the description is posted. Cached by head SHA, commits and template, and not by the current description, so an unchanged MR costs $0 the second time and applying a draft does not make the next ask a miss. `--dry-run` shows the pre-flight and whether it is cached and sends nothing; `--json` adds `description`, `unchanged` and `applied`. GitLab only for now: another forge says so and stops. Key `B` on the MR page opens the draft in an editor dialog (`enter` writes it to the MR, `ctrl+r` asks again past the cache, `esc` throws it away). |
| `ade ai ci-triage <mr-ref> [--refresh] [--dry-run] [--yes] [--override-budget]` | Triage of the failed jobs of the MR's pipeline: for each job (at most six) a one-sentence cause and a suggested fix, from the last lines of its log, read and cleaned the way the MR page's log viewer reads them. Nothing is written to the forge. Cached by what the logs say, not by job ids, so a retry that fails the same way is free. With no pipeline or no failed job nothing is asked. `--json` adds `failed_jobs`. Key `t` on the CI tab shows the answer under the job list (`J`/`K` scroll it). (`ade ai triage` is a different command: it triages an agent review's drafts.) |
| `ade inbox [--unread]` / `inbox show <id>` / `inbox read …` | Notifications. |
| `ade audit [--since 1d] [--action 'git.*']` | The append‑only action log. |
| `ade audit tail [-n 10] [--follow] [--action …]` | The newest entries, then (with `--follow`) every entry any `ade` process appends, until interrupted. `--json` prints JSONL. |
| `ade config check [--manifest <file>]` / `ade doctor` | Validates config and manifests (with their `*.local.toml` overrides; `--manifest` checks only those files and works before a user config exists, the manifest's `forge` name then being a warning); checks tools, paths (warns when `records.dir` is inside a git work tree), file watching (fsnotify, or polling), the resolved editor, forge tokens (with a read token: both tokens, that the read token cannot write, that both are the same account, and whether agents are kept from the write token), each forge's `ca_file`, the GitLab version and edition (with a warning per feature this release lacks: bulk publish, reviewers, work-item GraphQL, cadences) and the headless-CDE group (display, VS Code remote CLI, OSC 52 clipboard, nix, direnv). A `dotfiles` group lists each project with `[dotfiles]` and the commit last applied; a warning when it was never applied. |
| `ade config schema [--manifest] [--write DIR]` | Prints the JSON Schema of the user config (or of a manifest) generated from the Go structs, for editor completion in taplo / VS Code Even Better TOML. The committed copies are in `schema/`. |
| `ade cache reset [--yes] [--dry-run]` | Deletes `cache.db` and rebuilds the AI result cache and the spend ledger from the records. Says how many unsubmitted review drafts and unread notifications are lost and asks first (`--yes` skips the question); refuses while workspace instances run. |
| `ade ws install [worktree] [--force]` | Runs the `[repos.<r>.hooks] install` commands in every worktree the workspace uses (the trees its required repos and services run from, then the worktree itself), each inside its repo's dev shell, with ADE's environment. A worktree whose commands already succeeded is skipped; the result is remembered per worktree, keyed by a hash of the commands, of the lockfiles at its root (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lockb`, `go.sum`, `Cargo.lock`, `poetry.lock`, `uv.lock`, `flake.lock`) and of the worktree's creation, under `<data>/state/install/`, so the commands re-run only when one changes or with `--force`. A failure is reported, stops that worktree's commands, is not remembered and is recorded (`<marker>.failed`), so panes waiting for the install stop with its reason; the next run clears it. Every command is audited as `git.hook` with `hook=install`. `ade ws up --no-zellij` runs the same step first. |
| `ade task run <node> [--worktree <dir> \| --project <name>] [--after-install] [--wait-requires] [--wait-timeout 10m]` | Runs one node and follows its output (the services tab's pane command). `--after-install` waits until the install hooks of the node's worktrees have succeeded. `--wait-requires` starts only the node: it waits until each service it requires is running and ready, started by its own pane or another workspace. A wait prints `still waiting for <node> (<probe>) <time>` every 30 seconds, ends with the reason when the install or the required service's pane failed, and ends with a non-zero exit after `--wait-timeout`. A node another workspace already runs is not started twice: the pane says `already running (pid N)`, holds it and shows its log. `--project <name>` runs the node for the project instead of a worktree: repos resolve to their baselines (or `--with` pins) and the instance is held by `project:<name>` (the standalone services tab uses it). A node runs in its manifest `dir` and, when it has `prepare`, runs that first (only while `prepare_if_missing` does not exist; [manifest.md](manifest.md#working-directory-and-prepare-step-of-a-node)). |
| `ade services status [names…] [--project <name>] [--watch]` | Project-wide service status, outside any worktree tab: every declared `[services.*]` node and every node with an instance, each instance with its state (`ready`, `starting`, `blocked by …`, `dead`, `done`), port, worktree and holders (`held by web/main, project`); a declared service that runs nowhere is `stopped`. `--json` prints `[{project, services: [{node, declared, state, instances: [row…]}]}]`, the rows being those of `ade ws status`. Without `--project`: the project cwd is in, else every project. `--watch` refreshes every 2 s on a terminal. |
| `ade services up [names…] [--project <name>] [--with repo=branch] [--detach]` | Starts the named nodes (default: every `services.*`; a name is a node id, the bare name of a service, or a group) and what they require, over the project's baseline trees or pins, after the install hooks. Shares instances with workspaces. Stays until Ctrl-C (stops what it started, nothing a workspace holds); `--detach` leaves them running. |
| `ade services down [names…] [--project <name>] [--force]` | Releases the project-level hold and stops the instances nobody else holds, dependents first; without names it covers every instance of the project in any worktree. Instances a workspace still holds are listed as still running; `--force` drops those holds too and stops `keep = true` services. `--json` prints `{stopped, still_held}`. |
| `ade services install [names…] [--project <name>] [--with repo=branch] [--force]` | The install hooks of the trees those nodes run from, as `ade ws install` does for a worktree. |
| `ade services open [names…] [--project <name>] [--with repo=branch]` | Opens (or focuses) the project's own `<project> · services` tab in the zellij session: the install pane, then one pane per node, each `ade task run <node> --project <name> --after-install --wait-requires`. Outside zellij it prints the `ade services up` to run instead. |
| `ade ws layout [worktree] [--services]` | Prints the KDL of the workspace tab; `--services` prints that of its background services tab. |
| `ade ws restart <node> [worktree]` | Restarts a node and everything in the workspace that requires it (dependents first, then back up in dependency order); other instances keep running. Use it on a blocked service. |
| `ade vscode workspace [<item-ref\|worktree>] [--group <name>] [--project <p>] [--open]` | Writes a multi-root VS Code workspace (`<n>-<slug>.code-workspace`, in the item's records directory) with every repo of the project: the item's worktrees where it has them, baselines elsewhere, plus the run graph as tasks. `--open` runs `code`; otherwise it prints the path. Home `v` does the same. `--group <name>` names a `[repo_groups]` entry: alone (with `--project` when several projects are cloned) it regenerates that group's `<workspace>.code-workspace` in the project directory (the file `ade update` keeps; folders are the group's baselines) and prints it; with an item or worktree, the item's file holds only the group's repos (item worktrees where it has them) and is named `<n>-<slug>-<group>.code-workspace`. |
| `ade cd <item-ref\|repo> [--repo <name>] [--json]` | Prints one absolute path and a newline, everything else on stderr; on failure it exits non-zero with nothing on stdout, so a shell function can tell it failed: `cd ""` succeeds in bash and zsh, so a bare `cd "$(ade cd 412)"` stays where it is without an error (shell function: `adecd() { d=$(ade cd "$@") && cd "$d"; }`, which cds only when `ade cd` succeeded). `<item-ref>` is what `ade item` and `ade vscode workspace` take (tracker, child or MR ref, or a bare number with one project); the path is the item's worktree in its primary repo (the repos it routes to, in order, then the others by name) or in the repo `--repo` names (an error listing the repos it has when there is no worktree there). An item with no worktree is an error naming `ade start <ref>`. A name that is not a ref is a repo, `api` or `<project>/api` when several projects have one, and prints its baseline worktree (the default branch's tree). A ref wins when a string could be both: anything with `#` or `!` and a bare number is a work item. Cache and file system only, no network: a bare number reads the project's manifest snapshot from the last `ade update` (an error saying so when there is none). `--json`: `{path, project, repo, branch, worktrees: [{repo, path, branch, primary}]}`. |
| `ade notify send --title … [--kind … --subject …]` | Records a notification; a running dashboard shows it as a pop‑up. |
| `ade notify test [--severity warn]` | Runs the `[notify.external]` command once with a sample `notify.test` event, ignoring its kind filter and dedupe window, and exits 1 with the reason (stderr, "timed out after 10s") when it fails. See [setup.md](setup.md#external-notification-command). |
| `ade prompt [--format …] [--scope all\|project] [--zero] [--path <dir>] [--json]` | Shell-prompt segment: the current worktree's ticket (`ade.commitPrefix`, else `#<ade.parent>`) and `!N`, the count of items waiting on you (assigned, not done, court = you) plus open MRs asking for your review, e.g. `GL-412 !3`. Reads the worktree's git files and `cache.db` only: no network, no git process, no audit line, no migration; about a millisecond of work. Silent (nothing printed, exit 0) outside `<root>/<project>/<repo>`; at a repo or baseline tree it prints the count without a ticket. `--format` takes `{ticket} {attention} {attention_n} {items} {reviews} {project} {repo} {branch} {worktree}` (empty values and the blanks round them vanish; `{attention}` is `!N`, `{attention_n}` is N, both empty at 0 unless `--zero`). `--scope project` counts only the directory's project. `--json` prints `in_tree`, `project`, `repo`, `worktree`, `branch`, `parent`, `prefix`, `ticket`, `cache` (`ok`, `missing`, `error`) and `attention` `{items, reviews, total, synced_at}` (also outside a tree: `{"in_tree": false}`). Setup: [setup.md](setup.md#shell-prompt). |

Every command takes `--json`. `--debug-http` (global) logs every forge and AI HTTP request to stderr, with credentials and bodies never shown.

## Configuration

- **User config:** `~/.config/ade/config.toml`, or `$ADE_CONFIG`. It holds forges and their credential *commands*, `[[projects]]`, and the `[update]` and `[notify]` settings (`[notify.external]` hands budget and long-outage events to a command of yours).
- **Project manifests:** `*.ade.toml`, shareable. They define repos, the dependency graphs, and team conventions.
- **Local overrides:** `config.local.toml` and `<name>.ade.local.toml` beside either file, never shared: tables merge key by key, everything else replaces (PLAN.md §2).
- **Editor:** `host.editor` (`auto`, `nvim`, `ade-nvim`, `code`, `$EDITOR`) picks the editor everywhere ADE opens one; `auto` is `code` inside a VS Code terminal, else nvim, else `$EDITOR`.
- **Dev environment:** `s` (start work) and `w` open a zellij tab per worktree: a main pane (your editor, or `omp` started with an ADE-generated *implement* skill that carries the ticket, MR, conventions and your notes and stops for review without pushing, or a shell), the item's live overview (`ade item <ref> --watch`), lazygit, a shell, and a strip with the workspace's own tasks (none starts by itself: a pane waits for Enter, Ctrl-C stops one, Enter starts it again). The first time a workspace tab is opened, ADE also creates an unfocused `<tab> · services` tab: its first pane runs the repos' `install` hooks (`ade ws install`), then one pane per service of the run group starts on its own, in dependency order, each waiting for the install and for the services it requires; a service some node requires, with a `port` and no `ready`, counts as ready once the port accepts connections (also in its own pane). Services already running for another workspace are reused, not started twice. `[workspaces.<w>] services = "manual"` skips the tab and keeps the services in the strip, waiting for Enter, with a `services` pane that starts them all. `host.layout = "code" | "agent" | "manual"` is your default main pane (it beats the manifest workspace's `layout`); `a` in the start dialog, `ade start --layout` and `W` on Home pick the other one for a tab. See PLAN.md §6.6.
- **Fresh without a sync:** dialogs (`c` classify, `s` start work, `=` weight, `n` notes, `>` sprint move) read only their own issue and never wait for a running sync; after a write, and after `ade start` or the start dialog created a child and MR, that one item is read again and its cache row replaced, so Home and `ade item --watch` show it at once (no `ade sync`). The next full sync reconciles anything the one-item read could not see.
- **Notes on ongoing work:** `N` on Home opens a one-line form (`ade note` does the same from the shell): type the note, `enter` saves, `esc` cancels; a leading `!` or `tab` marks it blocked. The side panel lists the newest three dated notes under `notes` (blocked ones in the warning colour); the notes are read once per refresh. They live in the item's record, are never sent to the forge, and are added to agent and AI prompts like the rest of your notes.
- **AI research, MR description and CI triage:** with AI set up, `R` on a Home item opens its research: none yet (`enter` starts one in the background), running, failed (`enter` tries again) or done, with the answer to scroll; a cost question the caps raise is asked in the dialog, and a refusal says so. The side panel carries a `research` line once an item has a job. On the MR page `B` drafts the description (preview in an editable dialog, `enter` writes it) and, on the CI tab, `t` triages the failed jobs. All three run through the same pre-flight, caps, result cache, ledger and audit as every `ade ai` call, never block the page, and are absent with `ai.mode = "off"`. See `ade ai research|describe|ci-triage` above.
- **Job logs:** `l` on a CI job opens its log over the whole screen (title line, log, hint line). `j`/`k`, `pgup`/`pgdn`, `g`/`G` scroll, `h`/`l` move sideways, `/` searches (`n`/`N` step through matches, `esc` clears), `esc` closes. ADE reads the last 512 KiB of the log; the title says when the start was cut off. Colour codes are stripped, tabs expand to 8-column stops, other control characters are dropped, a progress line shows its last state, and GitLab section markers show as `── name` headers.
- **Last working day:** with AI set up (`ai.mode` not `off`, a profile configured), Home opens with a `Last working day` block. The day is the last one before today on which you pushed commits or opened or merged an MR, found in the past two weeks of forge activity rather than from the calendar. The block holds a short AI summary of that day in up to three sections (**Shipped**, **In progress**, **Reviews and discussion**). It is asked for once a day, when Home first loads, and the AI cache makes a repeat free. It is skipped when the budget is critical (90% or more of any cap) or the call would need confirmation; the block then lists the day's facts and says why there is no summary.
- **Retro:** opening the Sprint review page (`V`) writes its AI narrative under the same rule, as a structured retro: **Outcome**, a **Timeline** of what landed in date order, **Carried over** and **Velocity**. Skipped or failed automatic runs stay quiet; `n` on the page still asks on demand.
- **Sprint review with several projects:** `V` opens the review on the first project that has sprints and names it in the page header; `p` cycles the projects (the key and its footer hint appear only when two or more projects have sprints). `ade sprint review` and `ade sprint velocity` without `--project` do the same and say which project they chose in the warnings (`velocity` prints it on stderr). When no project has sprints they fail with `no project has sprints`.
- **Agent runs:** every agent process ADE starts (`ade agent plan|run|address`, and the `omp` pane of the `agent` layout) has `ADE_AGENT_RUN=1` in its environment. ADE's own push (`ade agent push`) does not, so a global `pre-push` hook can refuse any push made while the variable is set (sample in manifest.md). It is a guardrail, not a sandbox: the agent still has the forge token in its environment (only the read token, when the forge sets one).
- **Commit prefix:** `conventions.commit_prefix = "GL-{parent}"` in the manifest prefixes the first commit of the MR only (agent prompts state the expanded prefix, or that the project sets none): ADE's agent commit while the branch has none ahead of the target, the GitHub start commit and the squash message it sends. It is written per worktree (`ade.parent`, `ade.commitPrefix`, `ade.target`) for your own commit-msg hook; manifest.md has the hook.
- **Schema:** `schema/{config,manifest}.schema.json`; put `#:schema <path or URL>` on the first line of a TOML file.
- **Read and write tokens:** `[forges.<name>]` takes `read_token_env` / `read_token_cmd` beside `token_env` / `token_cmd`. With a read token, reads (sync, dashboards, AI context, clone and fetch) use it, only writes and `git push` use the token, and agents ADE launches do not inherit the token's `token_env`. `ade init` / `ade setup` accept `--read-token-env` / `--read-token-cmd`. See [setup.md](setup.md#a-read-token-and-a-write-token).
- **Self-hosted forges:** `[forges.<name>]` takes `ca_file` (PEM bundle; `SSL_CERT_FILE` also works), `ssh_port` and `max_concurrency` (default 4) besides `url`, which may carry a path prefix. Manifest: `repos.<r>.devshell = "auto" | "direnv" | "nix" | "none"` runs a repo's panes, tasks and services inside its dev shell ([manifest.md](manifest.md#dev-shell-per-repo)). Setup: [setup.md](setup.md#self-hosted-gitlab).
- **Reviewer group:** `conventions.mr.reviewer_group = "acme/reviewers"` makes start work request review from that group when it opens the MR: on GitLab the group's active members (you excluded) become the MR's reviewers (Free keeps one), on GitHub the team `org/team-slug` of the repository's owner is requested after the PR exists. The dry run and `--json` show the request; an unreadable group is a warning and the MR is opened without it, and a template's `/assign_reviewer` still applies ([manifest.md](manifest.md#starting-work)).
- **Project-wide setup:** the manifest's `[project]` table (`agents`, `packages` + `nixpkgs`) makes `ade project add` / `ade update` write `<root>/<project>/AGENTS.md` and `.ade/shell`; panes, tasks and services run through the shell when packages are set ([manifest.md](manifest.md#project-wide-setup)).
- **Palette:** `:` opens the command palette on Home, Worktrees and the MR page; every key of each page's help is an entry, so a terminal that swallows keys (a web tty) still reaches every action by name.

## Sandbox

Synthetic GitLab and GitHub data for development. Nothing here touches your real config:

```sh
. scripts/sandbox/env.sh        # isolates state under ./.sandbox, reads GITLAB_PAT from .env
go run ./cmd/ade project add scripts/sandbox/manifests/gitlab.ade.toml
go run ./cmd/ade project add scripts/sandbox/manifests/github.ade.toml
go run ./cmd/ade dash
```

`scripts/sandbox/{gitlab,github}-seed.sh` (re)create the remote sandbox data idempotently.
